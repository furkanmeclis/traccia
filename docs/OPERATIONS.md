# Shared operation contracts

The shared registry implements the T01 contract foundation, T03 durable mutation boundary and T04 workspace delivery path. Seventy-seven workspace, credential, activity, delivery, team, workflow, label, project, contributor, milestone, resource, member-discovery, product, environment, issue and relationship operations are bound to the shared registry, product HTTP router and a real MCP SDK server module. The panel exposes workspace and credential controls plus the activity feed; delivery status and replay are available through the shared operations and HTTP API without a panel approval step. The complete approved product inventory and network MCP transport remain roadmap work; SDK module acceptance currently uses in-memory connections. Test fixture mappings are not live endpoints.

## Contract and dispatch

`New[Input, Output]` takes concrete struct DTOs, stable metadata, a typed semantic validator and an optional typed use case handler. Input, output and public error contracts are concrete JSON Schema 2020-12 documents. A schema refiner can add constraints shared by both transports. A missing handler declares an operation with `available: false`; it never becomes callable because it has a mapping.

`NewRegistry` checks identifiers, positive versions, scope, effects, permissions and HTTP/MCP mappings, rejecting duplicate IDs, HTTP method/path pairs and MCP names. `Catalog` returns independent schema copies. The version describes the current contract; incompatible revisions require an explicit adapter migration rather than silently changing existing clients.

`Execute` verifies the selected channel and required scope, then invokes the injected authorizer on every call. The authorizer resolves the authenticated actor from context and verifies token status, membership and the operation permission. A requested workspace ID is never a grant. Missing actors and mismatched workspaces fail before reaching the handler. The handler receives a scope whose fields cannot be populated by transport code. Account operations reject a workspace selection; workspace operations require one.

The same binding executes for panel, API and MCP. It checks exactly one JSON value, valid UTF-8, duplicate object keys at every nesting level, required fields, unknown fields, schema constraints and typed domain validation. Duplicate keys are rejected before schema validation and typed decoding so repeated struct objects cannot merge into a different value in the use case. Output is serialized and validated before it is returned. Validation uses `json.Number`, preserving integers beyond 2^53; results are never truncated. Public errors carry stable codes and field codes rather than downstream messages. The original cause remains available through `errors.Unwrap` for diagnostics; adapters must not expose it to clients.

## Schemas and dependencies

- `github.com/google/jsonschema-go v0.4.3` infers schemas from the actual DTO types. Required fields follow JSON tags. It is also used by the Go MCP ecosystem.
- `github.com/santhosh-tekuri/jsonschema/v6 v6.0.3` compiles and validates schemas and JSON values. The compiler disables external resource loading. The second library is deliberate: the pinned inference library treats `json.Number` as a string during type validation, which would reject exact numeric input. Converting numbers to float64 would lose fidelity.
- Schema `format` and content annotations are not enabled as assertions. Semantic validators must enforce UUIDs, dates, domain relationships and other semantic rules. Do not use an annotation as authorization or validation.
- Nested dynamic data needs a deliberately reviewed schema. Struct inference is not proof that a domain contract is complete, and a generic map is not an acceptable top-level operation DTO.

## Adapter requirements before production wiring

1. Resolve authenticated context through the real session or tool-token adapter. Never accept an actor or membership grant from a JSON body.
2. Implement the authorizer with current token revocation, workspace membership and permissions (T02/T41). Inherited global platform permissions and client-selected organization headers do not establish this product scope.
3. Bind real application services. Preserve workspace scope in repositories, object storage, search, jobs and realtime. The registry is not a substitute for scoped queries and constraints.
4. Map HTTP path/query/body and MCP arguments to the same DTO. Emit the documented HTTP envelope, request IDs and localized user-facing messages. Register real routes in OpenAPI and generate frontend types in the same change.
5. Keep the T05 conformance guard passing when adding product operations: actual HTTP registrations, SDK tool discovery, application contracts and OpenAPI must agree. A catalog entry alone proves no transport coverage. Add real domain operations, preferences and job lifecycle contracts as those services are implemented.
6. Bind every retryable mutation to the durable application runner described below. Workspace history and durable delivery are described in [DELIVERY.md](DELIVERY.md); a write effect alone does not implement these policies.

Product authentication, workspace persistence and HTTP adapters are implemented for the forty-six product operations. The full approved operation inventory and network MCP adapter remain outstanding. T05 checks all forty-six implemented product operations in CI. Framework tests exercise shared dispatch, authorization/revocation, numeric fidelity, schema failures, error sanitization and unbound operations with test-only use cases.


## Product transport coverage (T05 / TEC-792)

`mcpbindings.NewServer` constructs a fresh official Go MCP SDK server (`v1.8.0`) with all forty-six actual product tools. It opens no listener and authenticates no caller by itself. A caller adapter must supply verified context or untrusted bearer material through `WithToolCredential`; the shared authorizer then verifies the current token, audience, actor and selected workspace on every call. There is no deployed MCP HTTP endpoint or OAuth/discovery implementation in this slice. Those remain T18 work.

Tool arguments are a closed object with `input` containing the exact domain DTO. Workspace operations additionally require `workspace_id`; writes additionally require `idempotency_key`. Account operations reject a workspace option, and reads reject a retry-key option. A root MCP endpoint can therefore serve multiple workspaces without making workspace selection part of a domain DTO. Tool descriptions and schemas expose the caller's retry key directly; ordinary MCP callers do not need hidden `_meta` support. Reuse the same stable key and complete input on retries. Neither a generated server key nor a JSON-RPC request ID supplies mutation identity.

Success uses the exact DTO output schema and returns the validated JSON as raw `structuredContent` plus JSON text content. Domain failures return `isError: true` with sanitized public error JSON in text content, outside the success output schema. Tool `_meta` advertises `traccia/error_schema`, `traccia/operation_id` and `traccia/contract_version`; the error-schema annotation is a Traccia convention, not a standard MCP output-schema field. The binder validates the closed wrapper and error JSON without the SDK generic argument/defaulting path. Input schemas retain their original JSON Schema resource scope, including root and nested `$id` references.

`backend/internal/platform/contractcoverage` compares the application catalog with registrations captured from the actual product router, all pages of real SDK `tools/list`, and resolved checked-in OpenAPI. Discovery is inspected before the SDK client's generic `any` decoding so large numeric schema bounds retain their values. The checker validates operation identities, versions, HTTP methods/paths, binding options, complete input/output/error schemas, field requirements, constraints, closed nested objects and pagination fields. Mounted HTTP fixture tests verify path/query/header conversion, exact JSON fidelity and the actual error/status envelope mapping. PostgreSQL acceptance exercises the original ten workspace tools and the fifteen team foundation tools and HTTP handlers with current authorization, durable retry and complete pagination.

HTTP success wraps the exact domain result in `{success,data,meta}`. Domain errors become `{success:false,error:{code,message,details?},meta}`; the mapped field details contain their public message codes. HTTP middleware may instead return `UNAUTHENTICATED`, distinct from the domain `UNAUTHORIZED`, and body adapters can return `UNSUPPORTED_MEDIA_TYPE` (415). OpenAPI covers those transport exceptions plus cancellation (408), conflicts (409) and unavailable operations (503). The documented domain error schema remains separate from these transport envelopes.

Immutable positive and negative fixtures prove that missing operations, wrong methods/paths, omitted nested fields or pagination, weakened requirements/constraints, imprecise large bounds and opaque/open schemas fail with a diagnostic. `node scripts/sync-product-openapi.mjs --check` fails on generated schema drift without rewriting the file. Generation preserves numeric tokens and resolves each standalone schema's resources before embedding it in OpenAPI. CI also regenerates frontend API types and rejects a diff.

Coverage is deliberately limited to registered product operations. `testdata/legacy-http-exclusions.json` identifies every inherited OpenAPI method/path outside that catalog with a reason; missing, stale and product-annotated exclusions fail. Newly documented operations must have a product contract or an explicitly reviewed legacy classification. This manifest does not prove inherited CMS, administration, account/profile or settings MCP parity. Whole-application acceptance still requires auditing visible inherited links, migrating relevant product actions and hiding irrelevant inherited features. T19/T22 and later acceptance work cover the remaining approved inventory and end-to-end parity.

Run the offline guard with `cd backend && go test ./internal/platform/contractcoverage` and the schema embedding fixtures with `node --test scripts/product-schema.test.mjs`. Regenerate OpenAPI with `node scripts/sync-product-openapi.mjs`, then run `cd frontend && pnpm api:generate`. Database acceptance remains part of the existing CI PostgreSQL-backed `go test ./...` run; in-memory SDK tests do not replace it.

## Durable mutation retries and concurrency (T03 / TEC-790)

The product catalog uses contract version 2 for the retry/version contracts. The five product writes declare `idempotent: true` and require one `Idempotency-Key` header (1–200 bytes, no leading/trailing whitespace, commas, NUL or line breaks). Registry callers, including the SDK MCP adapter, supply the same key through `Call.IdempotencyKey`. A key belongs to one complete immutable submission; retry with the identical input. Read operations do not create receipts.

Receipt identity is actor + optional workspace + operation ID + contract version + key. Separate unique indexes enforce account and workspace scopes, including the nullable account workspace. SHA-256 covers length-delimited operation ID/version/workspace and canonical complete JSON input. Canonicalization sorts object keys and removes insignificant whitespace using `UseNumber`: integers above 2^53, Unicode strings and array ordering retain their exact values. Numeric lexical representations remain distinct: `1`, `1.0` and `1e0` have different fingerprints. Duplicate keys, invalid UTF-8, unpaired Unicode surrogate escapes, unknown fields and invalid input schemas fail before a receipt claim. Path values represented in DTOs, including credential IDs, are part of the input; expected versions are fingerprinted too.

The repository runner opens one PostgreSQL READ COMMITTED transaction and injects its `dbtx` context into all authorization and repository queries. It reauthorizes inside the transaction, claims with `INSERT ON CONFLICT DO NOTHING`, then uses a separate SELECT so a waiting competitor observes the committed winner. It reauthorizes again after that wait. The handler, serialization and output schema validation finish before receipt completion and transaction commit. Domain failures, output validation failures and cancellation roll back the claim and mutation together. No pending receipt is committed and no lease permits a later duplicate mutation. Workspace creation joins the ambient transaction rather than prematurely committing its owner membership.

A winner stores exact output JSON bytes in BYTEA; equal input replays those bytes even after a service restart or later resource edits. Transport envelopes may contain a fresh request ID. Changed input with the same key returns `IDEMPOTENCY_CONFLICT` (HTTP 409). New workspace edits require `expected_version`; UPDATE matches that version and increments it atomically. A new key with a stale version returns `VERSION_CONFLICT` (HTTP 409), while retrying an earlier successful key returns its original workspace version. Clients retain their draft after conflict and explicitly reload current state before a new submission.

Authorization is current on every replay: revoked/expired credentials, disabled users, inactive workspace members, workspace mismatch and wrong audience cannot recover old results. Delegated credential creation also compares the requested child audience, scope subset and lifetime to the current caller's grants before exposing saved bytes. Absolute creation-time expiry validation runs only for new issuance, so an old successful receipt remains a receipt rather than becoming a newly validated creation request.

### Sensitive results, key retention and disclosure

Credential creation is one issuance with authorized idempotent replay, rather than a promise of one response delivery. The credential table still stores only SHA-256 token hashes and list operations expose metadata only. The exact validated create result is encrypted in its receipt with AES-256-GCM using `APP_ENCRYPTION_KEY`; authenticated associated data binds actor, workspace, operation/version, key and fingerprint. No raw token is written to receipt storage, logs, frontend query caches or durable browser storage. Only the creating component retains returned secret state; responses remain `Cache-Control: no-store`.

Receipts have no automatic expiration or pruning in this slice. Operators must retain the encryption key while any receipt uses it. Key rotation requires an explicit migration that authenticates and reencrypts all affected receipts with old and new keys available before switching the configured key. Missing/wrong keys, modified ciphertext, context mismatch or incomplete receipts fail closed with `OPERATION_UNAVAILABLE`; they never rerun a successful mutation or mint a replacement token. Never delete successful receipts to recover from a lost key: doing so would violate one issuance. Encryption key loss prevents sensitive replay until the original key is restored. A future retention policy must retain a durable spent-key tombstone if response bytes are removed, and a multi-key rotation facility remains separate work.

## Team foundation operations (T06 / TEC-796)

The product aggregate composes workspace and team bindings under the existing current workspace authorizer and durable mutation runner. Team reads require current membership and `workspace.read`; writes require the workspace owner role and `workspace.write`. Global platform administration grants no access. No extra permission matrix or tool scopes are introduced. Capabilities in list/detail results are current presentation hints.

The fifteen additional operations are `teams.create/list/get/update/archive`, `workflow_statuses.create/list/update/archive/reorder`, and `labels.create/list/get/update/archive`. Their actual routes and concrete DTOs are generated into OpenAPI. HTTP path resource IDs are merged into domain DTOs by the adapter; supplying them again in a body is rejected. MCP callers supply those fields in the closed `input` object. List query fields include `limit`, `after`, `archived`; label lists additionally accept `team_id` (empty for shared labels). Omitted booleans default to false. Unknown/duplicate query fields, duplicate JSON keys, unknown body fields and path overrides are rejected. JSON bodies are limited to 1 MiB.

Every write uses an explicit durable retry key. Team/label edits and archive require `expected_version`; workflow writes require `expected_workflow_version`, and status edits/archive also require the status `expected_version`. Status create/edit/archive and reorder lock one team and compare the aggregate version. Reorder requires the exact active status ID set, rejects duplicates/foreign IDs, and changes all positions atomically. The maximum is 10,000 total statuses per team, including archived identities; the reorder schema accepts at most 10,000 IDs, within the HTTP body budget. Lists remain paginated without a hidden result window. Workflow pages read items and aggregate version in one repeatable-read snapshot; clients collecting several pages must restart if the aggregate version changes.

Team codes normalize to uppercase ASCII, match `[A-Z][A-Z0-9]{1,9}`, remain unique inside their workspace and cannot change or be reused after archive. New teams receive five editable Turkish default statuses, one per category. Status category IDs are `backlog`, `unstarted`, `started`, `completed`, `canceled`. At least one active status must remain. Teams, statuses and labels archive without hard deletion or restore in this slice. Archived team configuration is readable; writes and number allocation are refused. Label scope is immutable and either workspace-shared or one team. Names are case-insensitively unique among active labels in that scope.

The repository exposes a transaction-only issue-number allocator and assignment validator for later issue insertion. Allocation updates a team bigint counter atomically and rolls back with its ambient transaction. Assignment locks the team and selected labels, verifies the status belongs to that team and permits only active shared labels or labels from that team. There is no public number-reservation operation and no issue model or issue insertion endpoint in T06; integration into real issue writes remains T08.

`activity.list` gained resource/team identity in contract version 3 and now adds project context in version 4. Consumers must regenerate against the current schema; write contract versions and their durable receipts are unchanged.

Team/status/label mutation, canonical resource history, outbox envelope, consumer delivery and completed operation receipt commit together. The production activity consumer projects those canonical records into the existing workspace feed, including resource and team identity. Credential material never enters these events.

## Project foundation operations (T07 / TEC-797)

The project module adds twenty-one shared operations. Under `/v1/workspaces/{workspaceID}`, projects expose list/create, get/update and explicit archive/restore; `/projects/{projectID}/teams` exposes paginated contributors and complete-set replacement; nested milestones and resources each expose list/create, get/update and archive/restore. `workspace_members.list` exposes `/members` for paginated workspace member selection. Each operation has an equivalent MCP SDK tool and uses the existing workspace authorizer. Reads require `workspace.read`; writes require a current workspace owner and `workspace.write` for tool credentials. All writes require an idempotency key. No permission matrix or member-management interface is introduced.

Project settings contain name, a short plain-text summary, nullable lead user UUID and nullable ISO `YYYY-MM-DD` start/target dates. A lead selection must resolve to a current active workspace member with an active global account. Member discovery returns only public user UUID, name, surname, workspace role, membership activity and assignability; it never returns email or platform-user records. An unchanged historical inactive lead can remain during unrelated edits and restores. Start dates cannot follow target dates.

Projects support multiple contributing teams. Creation and contributor replacement require one to one thousand distinct team UUIDs. New associations require active teams in the same workspace. Existing associations to archived teams can be retained or explicitly removed; removed associations remain stored for history and future issue foreign keys. Contributor pagination filters association archive state; the returned team archive flag describes the team itself. Teams are referenced in workspace scope, not treated as separate tenants.

Project version is the aggregate concurrency boundary. Settings, contributor replacement and every child mutation advance that version. Child update/archive/restore also requires the child's own `expected_version`, plus `expected_project_version`. Contributor replacement uses `expected_project_version`; project edits/archive/restore use `expected_version`. Milestone/resource outputs and collection pages return `project_version`. Read pages and their version share a repeatable-read database snapshot; clients combining pages reject aggregate-version changes. All lists use bounded keyset pagination and scoped cursor anchors, returning `has_more` and `next_cursor`.

Archive preserves identity and relations. Archived projects block settings and child writes, and separately expose the owner's restore capability. Child restore requires an active parent. Historical inactive references survive project restoration; newly assigned issues must still satisfy current activity checks. The transaction-only project assignment resolver validates workspace, contributing team, optional project and its exact milestone before the existing team/status/label resolver runs. Project locks precede team locks, and contributor updates lock teams in UUID order. There is no issue creation endpoint in T07; T08 must call both resolvers and use the composite workspace/project/team and workspace/project/milestone foreign keys.

Resources are typed `document`, `repository` or `link` source references with title, HTTP(S) URL, summary, provider and reference metadata. Credentials in URL authority are rejected. No remote fetch occurs. These are source-document links and metadata, not internal rich-document bodies or revisions. T10/T47 must implement the selected Plate.js schema, editor, revisions and typed backlinks; inherited Lexical code is not the editor foundation.

Project and child mutations, parent/child CAS, completed receipts, canonical history, full immutable event snapshots and durable delivery registration commit together. Project activity carries project identity (`activity.list` contract version 4) so milestones/resources link to their parent context. Production activity projection consumes all project lifecycle events through the existing durable worker.

## Issue relationships (T09)

Eight additive operations live below `/v1/workspaces/{workspaceID}/issues/{issueID}/relations`: `set_issue_parent` (`POST /parent`), `set_issue_duplicate` (`POST /duplicate`), `link_issue_block` (`POST /blocks`), `unlink_issue_block` (`POST /blocks/unlink`), `link_related_issue` (`POST /related`), `unlink_related_issue` (`POST /related/unlink`), `list_issue_relations` (`GET`), and `history_issue_relations` (`GET /history`). Existing issue metadata writes and their versions are unchanged.

Relationships use stable issue UUIDs and composite workspace foreign keys. Parent and duplicate each permit one outgoing edge. Parent, blocks and duplicate graphs reject cycles. Related pairs have one unordered canonical row. Reads derive inverse relations from that same row; duplicate state exposes both the direct target and the final target of its chain. Identifiers in typed issue references reflect current team moves, while immutable history retains the references captured at the event.

Each issue has an independent relation version, initially 1 without writing on reads. Every mutation requires `expected_versions`, an exact array of affected issue UUIDs and positive expected relation versions. Setters accept a nullable `target_issue_id` and atomically replace the outgoing edge; replacing requires the source, previous target and new target versions, with repeated UUIDs collapsed. Every affected version increments once. An unchanged setter or duplicate active link is a conflict. Removal preserves an immutable edge tombstone; linking again creates a new edge UUID. New links require active issues and active teams. Removing existing links remains available to authorized owners when either endpoint is archived.

Every graph mutation acquires the workspace graph transaction lock before sorted issue UUID locks, then checks reachability and writes in the same transaction. It does not acquire project or team locks after issue locks. A mutation records immutable relationship history and canonical outbox/activity context for each affected issue, together with its revisions and durable idempotency receipt. Failed history or outbox insertion rolls back all of them. A replay still revalidates current credentials and membership.

List filters are `kind` (empty, parent, blocks, duplicate or related), `direction` (all, incoming or outgoing), and `removed`. The state is current regardless of filters; the state, duplicate chain and returned edge references share one database statement snapshot. Both relation and history lists paginate with scoped immutable anchors. Archived endpoints, issue moves and removed edges do not invalidate an anchor's ownership.

## Canonical Plate documents (T10)

Issue descriptions and project documents have one workspace-scoped canonical Plate document per owner. The additive document operations resolve/create/get/replace/patch/list revisions/get revision/restore/export and list backlinks; `issues.create_rich` creates the issue metadata and its first document in the same authorized transaction. The production registry contains 88 operations. Existing metadata writes retain their inputs and issue versions. Documents use independent UUID revisions and compare-and-swap writes with ordinary operation idempotency keys.

Canonical format `plate`, schema version `1`, document revision UUIDs and upstream Plate package versions are separate concepts. The closed node union supports paragraphs, h1–h3, blockquotes, horizontal rules, code blocks/lines, indent lists/checklists, links, tables/rows/cells/headers and scoped user/issue/project mentions. Element IDs are nonzero, hyphenated UUID strings; text leaves have no IDs. UUID case is preserved, but identity comparisons ignore spelling case. Unknown properties, node kinds and schema versions fail validation. Text, Unicode and CR/LF sequences are never trimmed or normalized. Layout values that cannot round-trip through the supported number representation fail visibly rather than rounding.

Content is limited to 512 KiB of canonical JSON, 2,000 total nodes and depth 32; patch batches contain at most 100 operations. These budgets are checked before recursive instance schema validation in both shared execution and the MCP wrapper. The new content-bearing document/rich-create inputs allow 4 MiB of raw JSON to account for escape expansion while retaining the 512 KiB canonical content limit. Released operation HTTP bodies retain their 1 MiB transport limit. Limit failures preserve caller content and return validation errors. Table spans must form a complete nonoverlapping grid; an empty row is valid only when previous row spans cover every column. Colors are restricted to hex forms, `transparent` and `currentColor`. Link protocols are HTTP, HTTPS and mailto.

Typed patches insert, remove, move or replace stable element IDs. A node replacement retains its root ID. A section patch preserves its selected top-level heading and replaces the following body up to the next heading of equal or higher rank. The caller must provide the exact ordered current member IDs. Overlapping targets, descendant moves, unknown IDs and invalid final trees fail atomically. Ordinary patches store immutable typed deltas without a full-content checkpoint; create, full replace and restore store checkpoints. Historical reads reconstruct the complete requested tree. Restore creates a new revision. Content is never paginated; only revision and backlink lists use scoped stable cursors.

New revisions, references, canonical activity, outbox events and idempotency receipts commit together. Owner and mention project locks are acquired in UUID order, followed by the rich-create team when present, then owner and mention issue locks in UUID order, then the document. This also accounts for implicit foreign-key reference locks. Reads retain archived owner content; archived owners cannot receive new document writes. Mention identities and backlinks use real workspace-scoped targets, while displayed mention values remain explicit stored snapshots.

JSON export returns the lossless `{format, schema_version, content}` import envelope as a string, with document identity and revision in separate response fields. HTML is derived from allowlisted tags, escaped text/attributes and typed bounded layout properties. Markdown export explicitly reports losses in node IDs, reference metadata, table geometry, styling and exact whitespace; canonical JSON remains the recovery format.
