# Durable events and consumer delivery (T04 / TEC-791)

Workspace creation/renaming and team/status/label mutations run through the T03 operation receipt transaction. That same PostgreSQL transaction writes the workspace mutation, canonical `workspace_history`, an immutable `outbox_events` envelope and one `event_deliveries` row for every matching named/versioned consumer registered at ingestion. Any write or output-validation failure rolls everything back. Replaying an operation receipt skips the mutation callback, so it creates no additional history, event or delivery.

The first production consumer is `workspace.activity.v1`, subscribed to workspace creation/renaming plus team, workflow-status and label mutation events. It builds the workspace activity projection from canonical history. Workspace payloads contain the name/version; team configuration payloads additionally contain resource and team identity; credentials, token hashes and sensitive operation receipts are not copied into events. Envelope identity retains the event ID, event version, actor UUID, workspace UUID, occurrence time and inherited tenant metadata. PostgreSQL prevents changing event identity and canonical history. Reusing an event UUID with different data fails, including differences in exact large numeric values.

## Ownership and transaction boundaries

The API only records events. `cmd/worker` polls PostgreSQL independently of the optional Redis/Asynq queue. The worker claims one available delivery with `FOR UPDATE SKIP LOCKED`, increments its attempt count and stores a fresh lease token before running the handler. Claiming one at a time avoids consuming another delivery's lease while waiting in a batch.

Processing locks the claimed receipt and verifies its current token and unexpired database lease. The activity repository joins the processing transaction through `dbtx`; the projection and fenced success acknowledgement commit together. Handler errors, cancellation, lease expiration before acknowledgement or a process crash roll back the projection. A crash after commit leaves a successful receipt. A stale worker cannot acknowledge or retry a reclaimed delivery, and projection event uniqueness protects against repeated insertion.

Leases, backoff and replay eligibility use `clock_timestamp()` in PostgreSQL. Failed attempts persist bounded exponential backoff (1 second to 5 minutes) and become quarantined after eight attempts by default. A reclaim sweep applies the same backoff and attempt budget to expired processing leases, including a worker that died or repeatedly exceeded its lease. Locked live transactions are skipped. Missing consumer implementations fail with `consumer_unavailable`; they never produce a successful receipt. Each consumer's success, failure, lease and retry schedule is independent.

The worker waits for its delivery loop to stop before closing its database pool. Existing Redis tasks keep their own lifecycle; they are not the durable event authority. The inherited in-process `events.MemoryBus` remains synchronous and fail-soft for legacy platform listeners and is explicitly outside this guarantee. Historic pre-T04 outbox rows are retained, with no fabricated consumer success or automatic backfill. Legacy event-level status columns are retained for migration compatibility and are not consumer completion status; use delivery receipts.

## Shared product operations

All operations use the common application registry, current membership and credential checks, generated input/output/error schemas, HTTP adapters and MCP-described mappings. The network MCP adapter remains separate roadmap work. Read operations use keyset pagination (`limit` 1–100, default 20; `after` from `next_cursor`). Activity and delivery pages are newest first in their canonical database order, even if workers finish out of order. Cursors are resolved only inside the authorized workspace.

- `activity.list`: `GET /v1/workspaces/{workspaceID}/activity`, MCP mapping `list_workspace_activity`. Requires `workspace.read`; workspace members can read. Returns typed actor/workspace/event identity, resource name/version, type/UUID, optional team UUID and occurrence time. The panel reads this same projection and refreshes while visible.
- `deliveries.list`: `GET /v1/workspaces/{workspaceID}/deliveries`, MCP mapping `list_workspace_deliveries`. Requires `workspace.read` and workspace owner role. Returns payload-free status, attempts, consumer/version, scheduling timestamps and an allowlisted error code. Lease tokens, payloads, raw provider errors and stack traces are excluded.
- `deliveries.replay`: `POST /v1/workspaces/{workspaceID}/deliveries/replay` with `{"delivery_id":"UUID"}` and `Idempotency-Key`, MCP mapping `replay_workspace_delivery`. Requires `workspace.write` and workspace owner role. Uses T03 receipt idempotency. Resets only the selected pending/quarantined or expired processing delivery; active leases and successful deliveries return `CONFLICT`. Successful siblings retain their receipt and effect. Retrying a replay operation with its original key returns its saved result and never resets work a second time. An explicit replay resets the selected retry budget to zero.

Stable error codes are `consumer_failed`, `consumer_unavailable`, `invalid_event` and `lease_expired`; the empty code means no current failure. A quarantined delivery requires investigation followed by an explicit replay. There is no automatic retention/pruning of canonical history, events or successful delivery receipts in this slice.

## Guarantee and limits

For the shipped PostgreSQL projection, effect and acknowledgement are atomic and event identity is unique. This does not promise exactly-once network transport. Future external handlers must use at-least-once delivery with event-ID deduplication at the destination; SMTP, realtime and webhook providers cannot join a PostgreSQL transaction. The durable handler contract requires effects to use repositories joining the ambient transaction. Legacy notification listeners are not registered as durable consumers.

PostgreSQL acceptance tests use isolated schemas and the real mutation, outbox, projection and lease queries. They cover concurrent claims, receipt replay, insert failures, side-effect rollback, stale ACK/retry, lease expiry, bounded retries, independent consumer failure, replay authorization and workspace isolation. Subprocesses exit abruptly after claim, after the actual activity projection but before acknowledgement, and after committed acknowledgement. Reclaimed work produces one durable effect. CI runs these tests against a PostgreSQL 18 service with synthetic job-local credentials and public extensions initialized before concurrent fixtures.
